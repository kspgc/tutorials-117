# 一、 為什麼需要類別？

### 從程序化到物件導向
剛開始寫程式的時候，通常會使用**程序化程式設計**。這種寫法簡單、直覺，但隨著功能的增加，會發現，麵條代碼越來越難維護了，因為**資料和邏輯是分離的**。

為了為了解決這個問題，**物件導向程式設計（Object-Oriented Programming, OOP）** 應運而生。


### 為什麼需要類別?
在傳統的程序化程式中，我們習慣把**資料**存在變數裡，把**動作**寫成函式。

但是缺點是:
- 資料與函式沒有綁定: 負責處理角色血量的函式，被傳入速度。
- 命名混亂與衝突: health是誰的血量? name是誰的名字?
- 很難擴充: 要加上第二個player，要複製一遍?

因此，為了避免這些問題，出現了類別 `Class` 。
類別就像一個藍圖，可以把各種的資料(屬性)、行為(方法)綁一起，形成一個獨立的封閉的個體。而這就叫封裝。

### 什麼是物件導向（OOP）及其核心價值
**件導向程式設計（OOP）** 是一種範式編成思考模式。主張將現實世界中的 **事物** 抽象化為程式中的 
**物件**。

- 類別 `class` : 可以理解成設計圖，定義一個東西有甚麼規格和行為。
- 物件 `object` : 實體化後的設計圖，可以針對其獨立操作。

那又有哪些優勢呢?

1. 高內聚: 關聯資料都在一起，不會東一坨西一坨的。
2. 程式碼復用: 寫好一個類，可以一下子搞出一堆的實體。
3. 維護性高: 修改功能時只需修改類別內部。

來個對比:

1. 不使用類別
```python

# 角色 1 的資料
hero1_name = "PlayerA"
hero1_hp = 100

# 角色 2 的資料
hero2_name = "PlayerB"
hero2_hp = 80

# 攻擊函式（功能）
def attack(hero_name, enemy_hp, damage):
    print(f"{hero_name} 攻擊 {enemy_hp}")
    return enemy_hp - damage

# 實際使用
hero2_hp = attack(hero1_name, hero2_hp, 20)
print(f"{hero2_name} 剩餘血量: {hero2_hp}")


```

2. 使用類別
```python
class Hero:
    # 建構子：用來初始化角色的資料（屬性）
    def __init__(self, name, hp):
        self.name = name
        self.hp = hp

    # 角色特有的行為（方法）
    def attack(self, enemy):
        damage = 20
        print(f"{self.name} 攻擊了 {enemy.name}！")
        enemy.take_damage(damage)
	
	# 內部方法
    def _take_damage(self, damage):
        self.hp -= damage
        print(f"{self.name} 受到了 {damage} 點傷害，剩餘血量: {self.hp}")

# 透過藍圖（類別）快速建立兩個具體的物件
hero1 = Hero("A", 100)
hero2 = Hero("B", 80)

# 物件之間直接互動
hero1.attack(hero2)

```

> 可以明顯看出來，案例二的架構優於案例一。


#### 程式碼維護差異對比

| 維護面向       | 不用類別（程序化）                                | 使用類別（物件導向）                                |
| ---------- | ---------------------------------------- | ----------------------------------------- |
| **新增角色**   | 必須手動複製並建立一堆 `hero3_name`, `hero3_hp` 變數。 | 只要一行程式碼：`hero3 = Hero("索爾", 120)`。        |
| **資料安全性**  | 任何函式都可以不小心修改 `hero1_hp`，容易引發 Bug。        | 資料被保護在物件內部，只能透過物件的方法（如 `take_damage`）來修改。 |
| **程式碼可讀性** | 變數與函式到處飄，專案變大時很難一眼看出誰是誰的動作。              | `hero1.attack(hero2)` 讀起來就像英文句子，符合人類直覺。   |

# 二、抽象概念實體化：類別與實例

好，經過上面所述，應該對物件導向和類別有一些概念了吧? 哪我們再往深處剖析。

### 1. 什麼是類別（Class）：定義物件的「藍圖」

**類別**就是那張**「設計圖」或「模具」**。它是一個抽象的概念，規定了未來製造出來的東西應該長什麼樣子，但它本身「不是」那個東西。

> 就像你不會說設計圖是房子，但房子是基於設計圖搭建的，所以房子的內容是設計圖給的。

類別主要定義了兩件事：

- **屬性（Attributes / Fields）**：物件擁有的**特徵與資料**（它「有」什麼）。
- **方法（Methods）**：物件能執行的**行為與功能**（它「能」做什麼）。

> 類別在程式執行時，**不會**佔用實際操作資料的記憶體空間，它只是負責宣告規格。占用者是實體。

### 2. 什麼是物件（Object）：根據藍圖創建的「實體」
**物件**（也常被稱為**實例 Instance**）就是根據設計圖**「實際製造出來的東西」**。

當你用類別（藍圖）在程式中宣告並建立一個物件時，系統才會在記憶體中配置一塊真正的空間，用來存放這個物件特有的資料。

- **一個類別，無限物件**：你可以用同一張設計圖，製造出無數個彼此獨立的物件。
- **狀態獨立**：每個物件都有各自的屬性數值。例如，用同一張人類設計圖，可以造出「30 歲的A」與「20 歲的B」，兩人的名字與年齡互不影響。


### 3. 生活中的類別比喻
#### 範例一：汽車設計圖 vs. 街上跑的賓士車

- **類別（汽車設計圖）**：
    - **屬性規格**：品牌、顏色、排氣量、目前時速。
    - **方法功能**：發動引擎()、踩煞車()、按喇叭()。
- **物件（實體車）**：
    - **物件 A**：一台「黑色」、時速「60 km/h」的「Toyota」。
    - **物件 B**：一台「紅色」、時速「0 km/h」的「Ferrari」。

#### 範例二：手機生產模具 vs. 你手上的 iPhone

- **類別（手機規格書）**：定義了要有螢幕尺寸、鏡頭畫素、撥打電話與上網的功能。
- **物件（你的手機）**：你從盒子裡拿出來、貼了保護貼、裡面裝著你個人照片的那台實體手機。

#### 範例三：鬆餅烤盤 vs. 鬆餅

- **類別（格子鬆餅烤盤）**：定義了鬆餅的形狀（方形、格子狀）。
- **物件（倒了麵糊烤出來的鬆餅）**：你可以烤出一塊加了「巧克力醬」的鬆餅，和另一塊加了「蜂蜜」的鬆餅。烤盤只有一個，但鬆餅可以有無限多個。

#### 4. 程式碼實作

以下是上述汽車的實作的一部份。

```python
# 定義類別（設計圖）
class CarDesign:
    # 定義規格（屬性）
    def __init__(self, brand, color):
        self.brand = brand    # 品牌
        self.color = color    # 顏色
        self.speed = 0        # 初始時速都是 0

    # 定義功能（方法）
    def accelerate(self, speed_up):
        self.speed += speed_up
        print(f"【{self.brand}】加速了，目前時速：{self.speed} km/h")

# ------------------------------------------------

# 實體化物件（根據設計圖造車）
my_toyota = CarDesign("Toyota", "白色")  # 實例化出物件 A
my_ferrari = CarDesign("Ferrari", "紅色") # 實例化出物件 B

# 操作物件的行為
my_toyota.accelerate(50)   # 輸出：【Toyota】加速了，目前時速：50 km/h
my_ferrari.accelerate(120) # 輸出：【Ferrari】加速了，目前時速：120 km/h

```

> 這裡的self表示的是 **實體** 自身，並非類的自身。

# 三、 類別的兩大核心要素與建構

如果把物件比喻為人類，**屬性**就是他的名字與身高（基本資料），**方法**就是他會走路與唱歌（行為動作），而**建構子**就是他「出生」的那一瞬間。

### 1. 屬性（Attribute）：物件擁有的資料狀態
**屬性**是用來記錄物件**靜態資料**的變數。它代表了物件「有什麼」或「目前處於什麼狀態」

- **狀態獨立性**：雖然大家都用同一個藍圖，但每個物件建立後，各自的屬性數值是**獨立不互相干擾**的。
- **生活範例**：
    - **車子物件**：擁有 `color` (顏色)、`speed` (目前速度)、`fuel` (剩餘油量) 等屬性。
    - **銀行帳戶物件**：擁有 `account_number` (帳號)、`balance` (餘額) 等屬性。

### 2. 方法（Method）：物件能執行的行為動作
**方法**是寫在類別內部的函式（Function），用來定義物件**動態行為**。它代表了物件「能做什麼」。

- **操作屬性**：方法通常用來改變物件自身的屬性狀態（例如：執行「煞車方法」會讓「速度屬性」歸零）。
- **呼叫方式**：必須透過物件**實體**來呼叫（如：`my_car.accelerate()`）。
- **生活範例**：
    - **車子物件**：能執行 `accelerate()` (加速)、`brake()` (煞車)、`honk()` (按喇叭)。
    - **銀行帳戶物件**：能執行 `deposit()` (存款)、`withdraw()` (提款)。

### 3. 建構子（Constructor）：初始化物件的起點
**建構子**是一個特殊的方法。它的唯一任務就是「**在物件出生（實體化）的瞬間被自動執行**」，用來幫物件設定初始資料。

- **為什麼需要建構子？** 確保物件一出生就是個「健全、完整的個體」。你不會希望造出一台「沒有顏色、不知道時速是多少」的幽靈車。
- **關鍵特徵**：
    - 當你使用 `new` 關鍵字（如 Java, JS）或直接呼叫類別名稱（如 Python）時，建構子就會被**自動觸發**。
    - 你可以透過建構子傳入參數，讓每個物件在出生時就擁有不同的特色。
    - 在 Python 中，建構子的名字固定叫 `__init__`；在 Java/C++ 中，名字則與類別名稱完全相同。

# 四、 程式碼的延伸與重用：繼承（Inheritance）
當我們手上有好幾個結構很像的類別時，如果每個類別都重寫一遍相同的屬性和方法，程式碼就會變得非常臃腫。**繼承**就是為了解決「重複代碼」而誕生的機制。

### 1. 什麼是繼承：讓子類別承接父類別的資產

**繼承**就像是現實世界中的遺傳。子代可以無條件繼承父代的財產與特徵。

在程式中，如果類別 B 繼承了類別 A：

- 類別 B 會**自動擁有**類別 A 定義的所有屬性與方法。
- 類別 B 不需要複製貼上 code，就能直接使用這些功能。
- 類別 B 還可以延伸擴充，加入自己**專屬**的新功能。


```python
# 類別 A：父類別
class Animal:

    def __init__(self, name):
        self.name = name  # 屬性

    def make_sound(self):  # 方法
        return "這是動物發出的聲音"


# 類別 B：子類別（衍生類別），繼承了類別 A
class Dog(Animal):

    # 類別 B 延伸擴充：加入自己專屬的新功能
    def wag_tail(self):
        return f"{self.name} 正在搖尾巴！"


# 建立類別 B (Dog) 的實例
my_dog = Dog("小黑")

# 自動擁有類別 A 的屬性
print(f"狗的名字是: {my_dog.name}")

# 不需要複製貼上，直接使用類別 A 的方法
print(f"呼叫父類別的方法: {my_dog.make_sound()}")

# 使用類別 B 專屬的新功能
print(f"呼叫子類別獨有的方法: {my_dog.wag_tail()}")
```


### 2. 實務概念：父類別與子類別

#### 讓子類別承接父類別的資產
在物件導向的專有名詞中，我們這樣定義這層關係：

- **父類別（Parent Class / Base Class / 基礎類別）**：被繼承的類別。它定義了最通用、最基礎的特徵。
- **子類別（Child Class / Derived Class / 衍生類別）**：去繼承別人的類別。它是父類別的「特殊化」版本。

#### 父類別與子類別
**判斷繼承關係的黃金法則：`is-a`（是一個）**   (重要重要!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!!)

當我們說「子類別 **是一個** 父類別」時，這個繼承關係才成立。

- 戰鬥機（子）**是一個** 飛機（父） -> 成立
- 電動車（子）**是一個** 汽車（父）-> 成立
- 狗（子）**是一個** 貓（父） -> 不成立！不能盲目繼承

#### 方法覆寫（Override）：展現專屬的特有行為
雖然子類別繼承了父類別的方法，但有時候父類別的預設行為對子類別來說「不夠用」或「不合適」。

這時候，子類別可以在自己內部寫一個**名稱一模一樣**的方法，來覆蓋掉父類別的行為，這就叫做**方法覆寫（Override）**。

```python
# 父類別：定義最基礎的汽車
class RegularCar:
    def __init__(self, brand):
        self.brand = brand

    def start_engine(self):
        # 傳統燃油車的發動聲音
        print(f"{self.brand}：引擎發動。")

    def drive(self):
        print(f"{self.brand} 正在前進。")


# 2. 子類別：電動車（繼承 RegularCar）
class ElectricCar(RegularCar):
    # 方法覆寫 (Override)：電動車發動不該有轟隆隆的引擎聲
    def start_engine(self):
        print(f"{self.brand}：啟動電源。")
    
    # 延伸新功能：一般車沒有充電功能，電動車專屬
    def charge_battery(self):
        print(f"{self.brand} 正在充電中...")


# 3. 子類別：賽車（繼承 RegularCar）
class RacingCar(RegularCar):
    # 方法覆寫 (Override)：賽車前進速度極快
    def drive(self):
        print(f"{self.brand} 以時速 300 公里前進")

# ------------------------------------------------

car1 = ElectricCar("Tesla")
car2 = RacingCar("Ferrari")

car1.start_engine() # 輸出：Tesla：啟動電源。
car2.start_engine() # 輸出：Ferrari：引擎發動。（賽車沿用父類別行為）

car1.drive()        # 輸出：Tesla 正在前進。（電動車沿用父類別行為）
car2.drive()        # 輸出：Ferrari 以時速 300 公里前進

# 測試子類別專屬功能
car1.charge_battery() # 成功執行
# car2.charge_battery() # Error! 賽車沒有這個方法

```


### 繼承的優缺點與常見陷阱
#### 優點
1. **大幅減少重複程式碼**：通用的邏輯只要在父類別寫一次就好。
2. **易於統一修改**：如果所有車子的前進邏輯要改，只要去改父類別的 `drive()`，所有子類別都會同步更新。
#### 缺點與常見陷阱
1. **強烈耦合（緊密綁定）**：  
    子類別與父類別綁得太死。如果有一天你修改了父類別某個方法的名稱，全天下繼承它的子類別可能集體崩潰。
2. **大猩猩與香蕉問題（The Banana/Gorilla Problem）**：  
    當你只想繼承父類別的「香蕉」功能時，因為繼承鏈太深，你被迫同時繼承了握著香蕉的「大猩猩」，甚至整片「熱帶雨林」。子類別塞滿了根本用不到的垃圾程式碼。
3. **過度承諾（違反現實邏輯）**：  
    如果建立了一個 `Bird` (鳥) 父類別，裡面有 `fly()` (飛) 的方法。當你要新增 `Penguin` (企鵝) 子類別時，企鵝因為承接了父類別，被迫也學會了 `fly()`，這時你必須大費周章去覆寫它並報錯，這就是設計上的失誤。(這也叫違反LSP)


> **現代軟體開發金句**：**「多用組合（Composition），少用繼承（Inheritance）。」**  
> 如果兩個類別不是強烈的 `is-a` 關係，只是想借用對方的功能，應該把對方當成自己的「屬性」放進來（我有這台機器），而不是直接當對方的「孩子」（我繼承這台機器）。


### 小結
- **繼承** = 程式碼的代代相傳，利用 `is-a` 判斷合理性。
- **覆寫** = 兒子雖然繼承了家業，但可以發展出自己的新手段。
- **戒律** = 不要為了少寫兩行程式碼而盲目繼承，階層太深會成為維護噩夢。

# 五、 規範與底稿的建立：抽象（Abstraction & Abstract Class）

在掌握了封裝與繼承之後，我們會發現一個新問題：當我們設計了 `Animal`（動物）或 `Vehicle`（交通工具）這樣的父類別時，我們真的應該允許別人直接製造出一個「純動物」的物件嗎？

「純動物」長什麼樣子？牠要怎麼叫？這在現實世界中是不存在的。這種**只存在於概念中、用來規範子類別的藍圖**，就是物件導向的最高指導原則——**抽象（Abstraction）**。

### 規範與底稿的建立：抽象（Abstraction）

在軟體工程中，抽象的本質就是**「隱藏實作細節，只保留規格介面」**。它告訴外部使用者這個系統「能做什麼」，但把「怎麼做」留給具體的子類別去煩惱。


### 1. 為什麼需要抽象：只關注「做什麼」，隱藏「怎麼做」

想像你開車時，只要踩下「油門踏板」，車子就會加速。

- 你不需要知道引擎內部汽油是怎麼點火的、活塞是怎麼推動的（**隱藏「怎麼做」**）。
- 你只需要知道踏板的功能是加速（**只關注「做什麼」**）。

在團隊開發中，架構師會先寫好「抽象規格」，強制所有工程師在開發子類別時都必須符合這個規格，這樣團隊寫出來的程式碼才不會各行其是。

> 要讓一個物件不知道其他的東西是甚麼

### 2. 抽象類別與抽象方法

為了在程式中實現這個概念，我們需要兩個核心工具：

- **抽象類別（Abstract Class）**：一種**半成品**的藍圖。它不能被直接拿來建立物件，唯一的目的就是**被繼承**。
- **抽象方法（Abstract Method）**：一種**沒有實作內容（沒有程式碼身體）**的函數。它只聲明了方法名稱和參數，像是一張「待辦清單」，強制規定子類別必須去實現它。

### 3. 無法被直接實體化的藍圖：強制約束力

抽象類別最強大的地方就在於它的**強制性**。

- 如果你嘗試執行 `animal = Animal()`，程式會直接**報錯**拒絕執行。
- 如果子類別繼承了抽象類別，卻「忘記」去實作裡面的抽象方法，程式同樣會**報錯**。

這就像是總公司發給各分店的「合約底稿」，規定每家分店都必須提供「結帳」功能，至於各分店要用現金、信用卡還是 Line Pay，由各分店自己決定，但就是**不能不寫**。

### 經典範例：定義「動物叫聲」的規格

在 Python 中，我們使用內建的 `abc`（Abstract Base Classes）模組來建立抽象類別：

```python
from abc import ABC, abstractmethod

# 定義抽象類別（無法被直接實體化的藍圖）
class Animal(ABC):
    
    def __init__(self, name):
        self.name = name

    # 定義抽象方法（沒有內容，只規範名稱）
    @abstractmethod
    def make_sound(self):
        pass # 這裡不寫任何實作邏輯

    # 抽象類別內也可以有普通的具體方法
    def sleep(self):
        print(f"{self.name} 睡著了。")


# ------------------------------------------------
# 子類別實作：強制實現特定邏輯

class Dog(Animal):
    # 必須實作父類別規定的 make_sound，否則會報錯
    def make_sound(self):
        return "汪汪！"

class Cat(Animal):
    def make_sound(self):
        return "喵喵～"

# ------------------------------------------------
# 實際測試

# 測試 1：直接實體化抽象類別
# try_animal = Animal("神秘生物") 
# 這行會直接報錯：TypeError: Can't instantiate abstract class Animal with abstract method make_sound

# 測試 2：實體化具體的子類別
dog = Dog("Dog1")
cat = Cat("Dog1")

print(f"{dog.name} 的叫聲是：{dog.make_sound()}") # 輸出：Dog1 的叫聲是：汪汪！
print(f"{cat.name} 的叫聲是：{cat.make_sound()}") # 輸出：Dog1 的叫聲是：喵喵～

dog.sleep() # 輸出：Dog1 睡著了。（繼承自父類別的普通方法）

```


### 抽象類別與一般類別的維護差異對比

| 特性         | 一般類別（Concrete Class） | 抽象類別（Abstract Class）        |
| ---------- | -------------------- | --------------------------- |
| **直接實體化**  | 可以（如 `car = Car()`）  | 不行！強制當作底稿。                  |
| **方法內容**   | 每個方法都必須寫出具體程式碼。      | 可以包含沒有身體的 `abstractmethod`。 |
| **子類別約束力** | 子類別可以自由選擇要不要覆寫方法。    | 子類別**必須**實作所有抽象方法，否則程式無法執行。 |
| **主要定位**   | 用來創造實際操作的物件。         | 用來當作軟體架構的**規範與合約**。         |

- **抽象** = 定義「合約與規範」，只管規格，不管細節。
- **抽象類別** = 蓋章保證「未完工」的藍圖，禁止直接使用。
- **核心價值** = 確保大型專案中，所有衍生出來的子類別都擁有整齊劃一的介面，避免開發者自由發揮導致專案失控。

# 打造統一的行為標準：介面（Interface）

在前面，我們學到了如何利用「抽象類別」來為有血緣關係的子類別建立底稿。然而，在大型軟體開發中，我們常常需要為**完全不相關的物件**制定統一的行为標準。這時候，我們就需要**介面（Interface）**。

### 1. 什麼是介面：物件之間的溝通合約（Contract）

**介面**在軟體工程中被定義為一張「行為合約」。

- 它只規定物件「能做什麼（Behavior）」，但完全不限制物件**「怎麼做（Implementation）」**。
- 介面內部**沒有任何實作程式碼**，它只是一堆方法名稱的集合。
- **簽字畫押**：當一個類別宣告要「實作（Implement）」某個介面時，就等同於簽下了合約。它必須保證寫出介面中所規定的所有方法，否則程式連編譯、執行都無法通過。

> **生活比喻：USB 接口規範**  
> 國際組織制定了「USB 介面規範」（這就是 Interface）。它規定了接腳尺寸和傳輸協定。  
> 不管你是**滑鼠**、**隨身碟**還是**小風扇**（它們彼此毫無血緣關係），只要你符合 USB 介面規範，就能插上電腦使用。電腦不需要知道你是滑鼠還是風扇，電腦只認那個 USB 介面。

### 2. 介面與抽象類別的異同
初學者最常問的問題是：「既然都有約束力，為什麼不都用抽象類別就好？」  
關鍵在於「**血緣關係」與「多重實作的彈性」**。

📊 核心差異對比表

|特性|抽象類別（Abstract Class）|介面（Interface）|
|---|---|---|
|**核心本質**|關係是 **is-a**（是一個）。代表**血緣與繼承**。|關係是 **can-do**（能做到）。代表**能力與合約**。|
|**實作完成度**|它是**半成品**。可以包含已經寫好的普通方法與變數。|它是**完成度 0%** 的純規格。不能包含任何具體實作。|
|**繼承/實作限制**|**單一繼承**。一個子類別只能有一個親生父親。|**多重實作**。一個類別可以同時簽署並實作多個介面。|

- **單一繼承的限制**：如果「電動車」繼承了「汽車」抽象類別，它就再也無法繼承「電器」抽象類別了。
- **多重實作的解法**：如果改用介面，一隻「鋼鐵人」物件，可以同時實作 `Flyable`（可飛行介面）和 `Weaponized`（可開火介面），展現極高的彈性。

### 3. 解耦（Decoupling）：讓程式碼高飛的關鍵

**解耦**是軟體設計的終極目標之一。意思是**降低程式模組之間的關聯性與依賴度**。

- **強耦合（Coupling）的壞處**：  
    如果你的線上商城系統（A 模組）內部直接寫死了 `LINE_Pay` 的付款邏輯（B 模組）。哪天 LINE Pay 壞了或老闆想換成 `街口支付`，你得把整個商城的程式碼拆開大改。
- **介面解耦的優勢**：  
    商城系統（A 模組）不直接找特定的支付工具，而是找一張叫做 `PaymentConnection` 的**介面合約**。商城只對介面說：「請執行 `pay()`」。  
    未來不管換成哪一家支付公司，只要對方符合這張合約，商城系統**一個字都不需要改**，這就達成了完美的解耦。

### 實務應用：多型（Polymorphism）概念的初步體驗

我們用一個「通知發送系統」來展示：如何透過介面，用同一行程式碼操控完全不同的物件（多型）。

由於 Python 沒有原生 `interface` 關鍵字，實務上我們使用**全抽象類別**或**鴨子型別**來實現介面。這裡我們用Java來實現：

```java
// 定義介面（純行為合約：可以發送通知的物件）
interface NotificationInterface {
    /** 所有簽約的類別，都必須實作這個發送方法 */
    String send(String message);
}

// 不同的類別各自簽約並實作（它們彼此沒有血緣關係，使用 implements）
class EmailService implements NotificationInterface {
    @Override
    public String send(String message) {
        return "寄出 Email 郵件：[" + message + "]";
    }
}

class SmsService implements NotificationInterface {
    @Override
    public String send(String message) {
        return "發送 SMS 簡訊：[" + message + "]";
    }
}

class LineBotService implements NotificationInterface {
    @Override
    public String send(String message) {
        return "LINE 機器人推播：[" + message + "]";
    }
}

// ------------------------------------------------
// 實務應用：解耦與多型展現
public class Main {

    // 核心系統：只跟「介面」溝通，參數型態宣告為介面（NotificationInterface）
    public static void sendVerificationCode(NotificationInterface notificationTool, String userMsg) {
        // 同一行程式碼，會根據傳入的實體物件自動切換行為
        String result = notificationTool.send(userMsg);
        System.out.println(result);
    }

    // 測試開始
    public static void main(String[] args) {
        String msg = "您的驗證碼是 1234";

        // 今天想用簡訊發送
        sendVerificationCode(new SmsService(), msg);       // 輸出：發送 SMS 簡訊：[您的驗證碼是 1234]

        // 明天想改用 LINE 發送，核心系統「配合發送驗證碼」完全不用改！
        sendVerificationCode(new LineBotService(), msg);   // 輸出：LINE 機器人推播：[您的驗證碼是 1234]
    }
}

```



- **介面** = 物件世界的**外交官**。它不管你內部怎麼運作，只要外交口徑（方法名稱）一致就能溝通。
- **核心價值** = 讓程式碼從「牽一髮動全身」的泥潭，升級為「隨插即用、自由擴充」的樂高積木。

# 多型（Polymorphism）

在掌握了「繼承」與「抽象」之後，我們終於來到了物件導向的最後一塊拼圖，也是威力最強大的魔法——**多型（Polymorphism）**。

多型的英文字根來自於 **Poly（多個）** + **Morph（型態）**，字面意思就是「多種型態」。

簡單來說，多型就是：**「用同一行程式碼，去操控不同的物件，並自動產生各自專屬的結果。」**

### 1. 為什麼需要多型？解決「無止盡的條件判斷」

想像一下，你在寫一個遊戲的「戰鬥結算系統」，當角色獲勝時，要播放各自的勝利動畫：

- 不用多型的寫法（傳統程序化）：  
    你必須寫一堆 `if-else`：如果角色是戰士，就呼叫 `warrior_swing_sword()`；如果是法師，就呼叫 `mage_cast_light()`。當遊戲有一百個角色，你的 `if-else` 就會長到崩潰。
- **使用多型的寫法**：  
    你只需要寫一行：`current_character.play_victory_animation()`。  
    不管傳進來的是誰，程式會**自動根據這個物件的真實身份**，去執行屬於牠的動作。


### 2. 多型發生的三個必要條件

多型不是憑空出現的，它必須建立在我們前面學過的基礎上：

1. **要有繼承/抽象關係**：所有物件都必須承接自同一個父類別（或抽象類別）。
2. **要有方法覆寫（Override）**：子類別們各自改造了父類別的同名方法。
3. **父類別衍生出的統一呼叫**：用父類別的規格去統一操控子類別物件。

### 一鍵啟動所有裝置

```python
from abc import ABC, abstractmethod

# 1. 抽象類別（定義統一規格）
class SmartDevice(ABC):
    def __init__(self, name):
        self.name = name

    @abstractmethod
    def turn_on(self):
        pass

# 2. 子類別們各自實作（方法覆寫）
class Light(SmartDevice):
    def turn_on(self):
        return f"{self.name}：逐漸變亮，調整為暖色光。"

class AirConditioner(SmartDevice):
    def turn_on(self):
        return f"{self.name}：開啟冷氣，設定溫度為 26 度。"

class Speaker(SmartDevice):
    def turn_on(self):
        return f"{self.name}：播放輕音樂，音量調整為 30%。"

# ------------------------------------------------
# 3. 多型的威力展示：統一操控的函式

def activate_home_mode(device_list):
    print("啟動「回家模式」...")
    for device in device_list:
        # 關鍵在這裡！這行程式碼完全不知道 device 具體是哪一種電器
        # 它只知道大家都是 SmartDevice，都有 turn_on() 這個方法
        print(device.turn_on())

# 🎬 實際測試
devices = [
    Light("客廳大燈"),
    AirConditioner("主臥冷氣"),
    Speaker("智慧音響")
]

# 把整串電器丟進去，一行程式碼搞定所有事情
activate_home_mode(devices)

```


輸出結果：

```text
啟動「回家模式」...
客廳大燈：逐漸變亮，調整為暖色光。
主臥冷氣：開啟冷氣，設定溫度為 26 度。
智慧音響：播放輕音樂，音量調整為 30%。
```


### 多型對軟體維護的驚人價值

如果今天公司賺錢了，智慧家庭系統要引進最新科技「**智慧窗簾（Curtain）**」，在傳統程式中你得修改 `activate_home_mode` 的內部邏輯；但在多型的架構下：

1. **對舊程式零修改**：你完全不需要去動 `activate_home_mode` 函式。
2. **隨插即用**：你只要新建一個 `Curtain` 類別，繼承 `SmartDevice` 並實作 `turn_on()`，然後塞進 `devices` 清單裡，程式就自動支援了！這在軟體工程中叫做符合**「開放封閉原則（Open-Closed Principle）」**。


### 補充：Python 特有的「鴨子型別（Duck Typing）」

如果你學的是 Python，多型還有一個更酷的進階變體。Python 是一門動態語言，它甚至不需要嚴格的繼承關係，只要你的物件「長得像、行為像」就可以引發多型。

> **「如果牠走起來像鴨子，叫起來也像鴨子，那牠就是鴨子。」**

在 Python 中，就算你的 `Curtain` 沒有繼承 `SmartDevice`，只要它內部剛好也有一個叫 `turn_on()` 的方法，丟進上面的 `activate_home_mode` 依然可以正常執行！這讓 Python 的多型變得極度靈活。

### 總結：OOP 四大特性

到這裡，你已經解鎖了物件導向的完整世界觀：

- **封裝**：把零件和機密包起來，做出一個個獨立的「機器人」（物件）。
- **繼承**：讓新機器人可以直接複製舊機器人的基本功能，不用重造輪子。
- **抽象**：制定機器人的「出廠規格說明書」，確保大家都符合標準。
- **多型**：按下一鍵啟動，讓所有不同型號的機器人同時整齊劃一地做出各自的絕技。
