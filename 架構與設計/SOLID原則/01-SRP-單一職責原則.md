SRP (Signle Responsibility Principle) #單一職責原則。


---
## 為什麼 SRP 最容易被誤解

這是SOLID中，最容易被誤解的原則。或許是因為名字，很多人認為 SRP 就是一個模組只能做一件事情。

很多人因此把它跟另一個常見的好習慣搞混：

> **「一個函式只做一件事。」**

那是一個好的重構習慣，但它**不是 SRP**。SRP 講的不是「做幾件事」，而是「**為誰而做**」。

兩者的差別，會在下面的例子裡看得很清楚：**一個只有 20 行的函式，也可以嚴重違反 SRP。**


---

## 定義: 模組

在談 SRP 之前，要先講清楚它管轄的對象——**模組**。
> **模組**：一份彼此關聯的程式碼或結構。

它可以是一個函式、一個類別、一個檔案，甚至一個套件。重點不是它的大小，而是它**作為一個整體被修改**。


---

## SRP 的描述

我們可以分三層描述。

第一層：改變的理由

> **任何一個軟體模組，都應有且只有一個可以被修改的理由。**

第二層：行為者

> **任何一個軟體模組，都應該只對一個使用者或系統利益相關者負責。**

因為系統的使用者或所有者，就是決定「修改理由」的人。只要這群人希望對系統做的變更相同，我們就可以把他們歸成一類——**這一類人，稱為一類行為者（actor）**。

第三層：最精確的版本

> **任何一個軟體模組，都應該只為一個行為者負責。**


---

## 到底是甚麼?

上面三層定義都對，但在實務上仍然抽象。所以我們把它翻譯成一句可以直接操作的問句：

>**「這段程式碼如果壞了，會是誰來找我改？」**
> **每一個「來找我改的人」，就是一個行為者。超過一個，就違反 SRP。**


---

## 行為者不是「別人」，是「角色」

「行為者」聽起來像是「**另一個人**」，但這是一個誤解。行為者的本質不是「人」，是「**一組獨立變化的需求**」。

這一段對獨立開發的人特別重要，因為很多人會這樣想：

> 「我又沒有團隊，行為者不就我一個？那我還需要 SRP 嗎？」

答案是：**需要，而且可能更需要。**

### 獨立開發的例子

假設你一個人做一款遊戲，你在同一個專案裡，其實同時扮演了好幾個角色：

| 你現在扮演的角色 | 他關心的事         |
| -------- | ------------- |
| 策劃       | 關卡節奏、數值平衡、玩法  |
| 美術       | 角色立繪、UI 風格、動畫 |
| 程式       | 效能、架構、可維護性    |
| 測試       | 邊界條件、例外狀況     |

**這些角色，關注的東西完全不同，會要求你改的地方也不同。**
這三件事**不會同時發生**，也**不該由同一段程式碼負責**。所以即使從頭到尾只有你一個人，這段程式碼**照樣違反 SRP**。

## 實例：`make_order()` 服務了幾個人？


來看一段出至於我們總務的真實的程式碼:
```python
@app.route('/api/order', methods=['POST'])
def make_order():
    data = request.get_json()
    items = data.get('items', [])

    if not items:
        return jsonify({"status": "error", "message": "購物車是空的"}), 400

    order_total = sum(item.get('price', 0) * item.get('quantity', 1) for item in items)

    with data_lock:
        assigned_number = db["current_number"]
        new_order = {
            "number": assigned_number,
            "items": items,
            "total": order_total,
            "order_time": datetime.now().strftime("%H:%M:%S")
        }

        db["orders"].append(new_order)
        db["current_number"] += 1
        db["total_revenue"] += order_total
        save_data()

    broadcast_update()

    return jsonify({"status": "success", "number": assigned_number})
```

這函式很短，就20多行，但是如果用剛剛的行為者切分，會發現，**它腳踏六條船，同時服務了六類行為者**。

| 行為者     | 他會來要求什麼       | 會改到哪一行                       |
| ------- | ------------- | ---------------------------- |
| 老闆 / 行銷 | 「我要加折扣碼」      | `order_total` 的計算            |
| 會計      | 「營收要加稅、要分開記」  | `db["total_revenue"] += ...` |
| 現場工作人員  | 「編號要跳過 4 號」   | `db["current_number"] += 1`  |
| IT / 維運 | 「存檔要改資料庫」     | `save_data()`                |
| 前端      | 「API 要多回一個欄位」 | `jsonify(...)`               |
| 後台人員    | 「通知要延遲 3 秒」   | `broadcast_update()`         |

**六個行為者 = 六個改變的理由 = 違反 SRP。**

`make_order()` 只有 20 行，但它**同時對六個人負責**。  
這並非函式太長的問題，是**它同時服務六個行為者**的問題。  
**一個很短的函式，也可以嚴重違反 SRP。**

## 常見的問題

### Q1：「如果兩個行為者的需求常常一起變，還要拆嗎？」

**要拆。但更精確的說法是：如果他們永遠一起變，那他們其實是同一個行為者。**

SRP 不是按人頭拆，而是按「**是否獨立變化**」拆。

- 行銷要改折扣，會計不會跟著改 → 兩個行為者

- 行銷要改折扣，一定會連動到發票上的金額呈現 → 很可能其實是同一個「商業規則」行為者，只是你以為是兩個

所以判斷行為者的標準不是「有幾個人」，而是「**有幾條獨立變化的軸線**」。

### Q2：「所以符合 SRP 就是每個類別都很小？」

不是。**大小不是判準，改變的理由才是。**

一個 500 行的類別，如果只服務一個行為者，它仍然符合 SRP。  
一個 20 行的函式，如果服務六個行為者，它違反 SRP。

## 小結

- SRP 講的不是「做幾件事」，是「**為誰而做**」。
- 模組 = 一組被整體修改的程式碼。
- 行為者 = 會來要求你改這段 code 的人（更精確地說是「一條獨立的變化軸線」）。
- **行為者不一定是別人，也可能是你自己扮演的另一個角色。**
- 落地問句：**「這段 code 壞了，會是誰來找我改？」超過一個人，就違反 SRP。**
- 修法：**把不同行為者的東西，拆到不同模組。**

## 拆完之後，還有一個問題

把 `make_order()` 拆成六個模組之後，SRP 的問題解決了——每個模組只對一個行為者負責。

但下一個問題馬上出現：

> **「明天要加折扣碼，你還是得回來改舊 code。」**

行為者分開了，**「新增」還是被迫變成「修改舊碼」**。

這就是下一個原則要處理的事——**OCP：開放封閉原則**。
