Open-Closed Principle #開放封閉原則

上一節我們把 `make_order()` 拆成六個模組，讓每個模組只對一個行為者負責。SRP 的問題解決了。

但下一個問題馬上出現：

> **「明天要加折扣碼，你還是得回來改舊 code。」**

行為者分開了，**「新增」還是被迫變成「修改舊碼」**。這就是 OCP 要處理的事。

---

## 定義

> **軟體實體（類別、模組、函式）應該對擴充開放，對修改封閉。**

翻成白話：

> **加新功能時，你應該可以「新增程式碼」來完成，而不是「修改舊程式碼」。**

這裡的「封閉」很容易被誤解成「code 永遠不能改」。**不是。** 它的意思是：

> **當需求是「新增一種變化」時，你不需要去動那些已經寫好、已經測試過、已經上線的舊 code。**

舊 code 當然可以改——但**改的時機**應該是「修 bug」或「重構」，而不是「每次加功能都要回來改」。



---


## 怎麼判斷

OCP 的違反有非常明顯的「味道」，通常長這樣：
```python
if type == "email":
    ...
elif type == "discord":
    ...
elif type == "ig":
    ...
```

或是
```python
if discount_type == "student":
    price *= 0.8
elif discount_type == "member":
    price *= 0.9
elif discount_type == "coupon":
    price -= 50
```


> 當你發現自己**每次加一個新東西，就要回來加一個 `elif`**，你就正在違反 OCP。

因為「新增一種類型」這件事，被迫變成了「修改一個已經存在的判斷式」。而那個判斷式，可能已經被三個人依賴、已經上線、已經有測試。

## `make_order()` 的違反OCP之處

### 一、折扣碼

現在 `make_order()` 裡的算錢是這樣：

```python
order_total = sum(item.get('price', 0) * item.get('quantity', 1) for item in items)
```

看起來很乾淨，因為**目前還沒有折扣**。

但我們用 SRP 那節的「行為者」角度想一下：**行銷**這個行為者，之後一定會來要求：

- 「學生證打八折」
- 「會員打九折」
- 「滿 300 折 50」
- 「週三第二件半價」

如果每一次都用最直覺的寫法，程式碼會長成：
```python
if discount == "student":
    total *= 0.8
elif discount == "member":
    total *= 0.9
elif discount == "over300":
    total -= 50
elif discount == "wednesday":
    ...
```


### 二、通知通道

`broadcast_update()` 目前只服務後台 SSE。但實際上，這套系統之後很可能會想加：

- 新訂單時寄 Email 給老闆
- 發 Discord 訊息到社團頻道
- 加 LINE Notify

如果每次都用「在 `make_order()` 裡多呼叫一個函式」的方式加，`make_order()` 就會越來越大，而且**每加一個通道，就要改一次 `make_order()`**。這同樣是違反 OCP。



---

## 解決方案: 把「變化」抽出來

OCP 的核心動作只有一個：

> **把「會變的那部分」抽成一個穩定的介面，讓新增變化 = 新增一個實作。**


原本:
```text
make_order()  ──直接判斷──>  email / discord / ig / line ...
```

修改後:
![[261111-1.drawio.png]]

**關鍵在於**：`make_order()` 從此不知道有幾種通知通道。它只知道「有一個東西叫 Notifier，我叫它 `send()`，它就會送」。

之後要加 LINE，**只需要新增一個 `LineNotifier`，`make_order()` 一個字都不用改。**

這就是「對擴充開放，對修改封閉」。


---

## 不要為了 OCP 而 OCP

> **不要看到 `if/elif` 就抽介面。**  
> **不要為了「以後可能會加」，就現在先抽象。**

OCP 不是「所有東西都要可以擴充」。它是「**當你預期某個地方會頻繁地新增變化時**，才值得付出抽象的成本」。

抽象是有代價的：

- 多一層介面 → 多一層閱讀成本
- 多一個檔案 → 多一個要維護的地方
- 過早抽象 → 你根本不知道未來的變化長什麼樣，抽出來的介面大概率是錯的

### 判斷該不該套用 OCP 的三個問題

|問題|如果答案是…|
|---|---|
|這個地方**已經**加過幾次類似的東西了嗎？|是 → 值得抽|
|這個地方**明確預期**會一直加新種類嗎？|是 → 值得抽|
|這個地方只是「**有可能**會變」嗎？|是 → **先不要抽**，等它真的變了再說|

一個只有 email 通知的系統，寫一個 `Notifier` 介面，然後只有一個 `EmailNotifier` 實作——這不是 OCP，這是**過度設計**。

> **OCP 是「當變化真的來臨時，讓你不用改舊 code」的能力，不是「預先預測所有變化」的義務。**

## 小結

- OCP：**對擴充開放，對修改封閉。**
- 白話版：**加新功能時，只新增程式碼，不改舊程式碼。**
- 識別訊號：**每加一種東西，就要回來加一個 `elif`。**
- 解法方向：**把「會變的部分」抽成介面，新增變化 = 新增實作。**
-  **不要為了 OCP 而 OCP。** 只有「已經在變」或「明確會一直變」的地方才值得抽象。
- OCP 不是預測未來，是**讓變化來臨時，舊 code 不用動**。
